# Tests

Automated and manual test assets for this project. Each subdirectory has its own README defining what belongs there.

## Layout

| Directory | What lives here | Base class | PHPUnit suite |
|---|---|---|---|
| [`Unit/`](Unit/README.md) | Tests that do **not** boot the framework. Pure PHP, no Laravel / Statamic dependency. | `PHPUnit\Framework\TestCase` | `Unit` |
| [`Feature/`](Feature/README.md) | Tests that **do** boot Laravel + Statamic. May depend on stache content, HTTP routes, database state. | `Tests\TestCase` | `Feature` |
| [`manual/`](manual/README.md) | Human-run smoke checklists (Markdown, not PHP). Used when automation is impractical. | — | — |
| [`Concerns/`](Concerns/README.md) | Shared traits mixed into test classes (reusable guards/helpers, not tests). | — | — |

## Running

```sh
# One file or one method - the everyday case
vendor/bin/pest tests/Feature/SomeTest.php
vendor/bin/pest --filter='it does the thing'

# Just one suite
vendor/bin/pest --testsuite=Unit
vendor/bin/pest --testsuite=Feature

# A scoped band - --exclude-group=serial is needed here too, not just whole-suite
vendor/bin/pest --parallel --exclude-group=serial tests/Feature/Scopes

# The whole suite - two steps, not one run. See below before reaching for this.
vendor/bin/pest -d memory_limit=4G --parallel --exclude-group=serial
vendor/bin/pest -d memory_limit=4G --group=serial
```

**`--exclude-group=serial` belongs on every `--parallel` run, including one scoped to a directory.** The flag reads like a whole-suite concern and is not: nine files under `tests/Feature/Scopes` alone carry `group('serial')`, so a band scoped to that directory runs tests the project deliberately excludes from a band. They then fail on shared state, which is what the group exists to prevent — and the failures present as ordinary assertion errors rather than as anything naming concurrency, so they read as a defect in the code under test. The cost of getting it wrong, measured here rather than imagined: a result published in four places and corrected in all four, after two concurrent sessions each classified a failure that should never have run — one of them against the wrong ticket's signature, correctly, and still wrong.

### The whole suite is the two-step shape, never a single process

`php artisan test`, and a bare `vendor/bin/phpunit` or `vendor/bin/pest`, run all 7,680 tests of `Unit` + `Feature` in **one** PHP process. That is not a supported way to run this suite, for two reasons that compound.

**It would take hours even if it could finish.** Measured on macOS on `main`, single process: the `Feature` phase runs at roughly **5.4 s per test**, which puts the 5,726 `Feature` tests alone near **8.6 hours** (an upper bound - the machine was busy). Nearly all of that is the per-test Laravel + Statamic boot a `Feature` test pays by design, which is also why the `Unit` phase clears 1,954 tests in under a minute and then appears to stop dead: it has reached `Feature`, and a two-minute pause inside the `Unit` phase is UAMS-Web/uams-statamic-archive#2401's four framework-booting files rather than a hang.

**And it exhausts memory long before it finishes.** None of those commands passes a `memory_limit`, so the run takes whatever the machine's CLI `php.ini` sets. [`scripts/local-ci.mjs`](../scripts/local-ci.mjs) passes `-d memory_limit=4G` to both halves - directly to the serial tail, and through `--passthru-php` to the paratest workers - so the gate never meets this. Measured with Herd's PHP 8.4, whose CLI default here is **512M**:

```
-d memory_limit=512M   fatal at test 2,126 of 7,680, 0 failures before it
                       "Allowed memory size of 536870912 bytes exhausted"
                       ... in Illuminate/Collections/Arr.php

-d memory_limit=512M   fatal at test 2,125 -- a second run, no instrumentation
                       same message, different allocation site:
                       ... in mitydigital/sitemapamic/routes/web.php

-d memory_limit=4G     test 2,192 and still running, zero memory fatals,
                       at a HIGHER resident size than killed either run above

-d memory_limit=256M   fatal at ~test 90, same shape
```

**Three things in that table are the argument.** The two 512M runs, one carrying a streaming event logger and one bare, died **one test apart** - so the count is reproducible and the instrument did not move it. They died at **different allocation sites**, which is what a ceiling looks like: the fatal lands wherever the next allocation happens to fall, not on a defective test. And the 4G arm walked past the index that killed both, while holding *more* memory - so the limit is the discriminator rather than anything about the tests near 2,125.

Baseline resident memory is already 350-400MB before the first `Feature` test runs, and it climbs from there, so **the default limit on a machine like this one cannot carry the suite to the end.** It gives out around a quarter of the way through, and the count moves with the machine and the limit rather than naming any test - which is why reports of it cluster near 2,100-2,600 without ever agreeing.

**A second end state has been seen, and it is not explained.** Two other single-process runs at the same default, on the same machine, did not fatal at all: they stopped emitting at 2,360 and 2,613 tests and then held roughly 90 percent of a core for 14 and 16 hours - no fatal, no exit, not another byte, and no memory message anywhere in their logs. Nothing establishes that those two are the same failure as the fatal above. A **single non-terminating test** produces that signature exactly, and needs no memory ceiling to do it; the proximity of the counts may be coincidence. Both processes were killed before anyone sampled them, so it cannot be settled from what survives.

**If you meet it, capture the one thing that separates the two.** At the moment output stops, record which test is executing - a per-test progress format rather than dots, or a stack dump of the pest process. That distinguishes "stuck in one test" from "crawling through many" in seconds, and it is what neither of those runs preserved.

**And confirm the process actually died.** This end state survives its own bound: killing the wrapper orphans the PHP process, which keeps running and keeps a core busy. `.claude/rules/long-running-commands.md` covers resolving and attributing one.

**So use the two steps above.** It is the shape [`scripts/local-ci.mjs`](../scripts/local-ci.mjs) and the `phpunit` CI job both run, and it spreads the suite over workers that each stay well below the ceiling.

## Picking the right directory

If you have a test in hand and aren't sure where it goes, the deciding question is:

> Does the code under test need Laravel's container, Statamic's stache, the database, an HTTP request, the filesystem under `content/`, or any facade?

- **No** → `Unit/`, extend `PHPUnit\Framework\TestCase`.
- **Yes** → `Feature/`, extend `Tests\TestCase`.

A test that *uses* Mockery to stub a dependency is still a unit test — it's the code under test, not the test's own helpers, that determines the classification.

### Never assert against "the first match" from a content query

A test that pulls one fixture out of a Stache-ordered query — `$query->get()`, take the first entry that qualifies, assert on it — is not testing the thing it names. It is testing **whichever entry the index happened to return first**, and that is decided by worker and index state, not by the code under test. The set it samples from is real content, so the sample silently changes as content changes.

The failure mode is not a flake, it is a **hidden green**. `PeopleLensRouteTest` rendered the first publicly-renderable person and passed on `main` for months while four entries in the same collection returned a 500 on every page (UAMS-Web/uams-statamic-archive#1883). Nothing was wrong with the test's assertions; it simply never drew one of the four. The bug surfaced only when an unrelated PR added eight tests, changed how paratest distributed work, and moved the query onto a broken entry — so the PR that *exposed* a pre-existing production bug looked like the PR that caused it.

Iterate the whole qualifying set instead, and collect failures rather than throwing on the first:

```php
$failures = [];

foreach ($people as $candidate) {
    if (! $controller->isPubliclyRenderable($candidate)) {
        continue;
    }

    try {
        // … exercise it …
    } catch (Throwable $throwable) {
        $failures[] = $candidate->slug().': '.$throwable->getMessage();
    }
}

expect($failures)->toBe([]);
```

Collecting matters as much as iterating: a bad entry then **names itself** instead of hiding the other thirty-nine behind the first stack trace. Keep the "no qualifying content" guard so a bare `content/` still skips rather than passes vacuously. If iterating the full set is genuinely too slow, pin a *named* fixture — never an ordinal one.

### Verifying a Feature→Unit move (the audit rule)

A grep for facades / `config(` / `app(` in a test file is a useful **prior**, but it is **not proof** the test is framework-free. The only authoritative qualification is empirical: move the file to the mirror path under `tests/Unit/`, drop its `uses(TestCase::class)` line and the `use Tests\TestCase;` import, and run it. It qualifies **only if it stays green with no assertion changes**. Two failure modes a static scan misses — both surfaced during the UAMS-Web/uams-statamic-archive#731 audit and both throw once the app is no longer booted:

- **The test leans on a container-backed helper.** `validator([...], [...])`, `__()` / `trans()`, or a validation rule referenced by its **registered string alias** (`['epic_dep_id']`) all resolve through the container — the alias only exists after a service provider boots. A rule test that calls `validator()` needs the app even though the rule itself is pure; rewrite it to call `(new Rule)->validate(...)` directly if you want it in `Unit/`, otherwise it stays a Feature test.
- **The class under test looks pure but resolves the container internally.** `App\Rules\UamsVideoUrl::validate()` delegates to sub-rules constructed via `app()`, so even a direct `(new UamsVideoUrl)->validate(...)` call throws `BindingResolutionException` with no app booted. `App\Support\RequestAttributeMemo` memoizes on the bound request singleton, so its caching silently no-ops without the framework. Neither is visible from the test body — only running it as a unit test reveals the dependency.

**First pass (UAMS-Web/uams-statamic-archive#731).** The three clusters that *looked* pure — `tests/Feature/Enums/`, `tests/Feature/Rules/`, `tests/Feature/Support/` (top level) — were audited this way. Eight files qualified and moved to `tests/Unit/` (all three `Enums/`, one `Rules/`, four `Support/`); six that a grep also flagged were reverted because they failed the empirical run (they need the container). The payoff is the per-class framework boot: the eight files ran in **~76 s** as Feature tests and **~0.5 s** as Unit tests — the same 60 tests and 130 assertions, ~150× faster — because a unit test skips the Laravel + Statamic bootstrap Feature tests pay (~15 s cold for the first class in a process; the warm per-`TEST_TOKEN` stache cache amortizes later classes, but the aggregate stays boot-dominated). The remaining ~390 `tests/Feature` files are a long-tail audit tracked in UAMS-Web/uams-statamic-archive#1317.

**Reverse pass (UAMS-Web/uams-statamic-archive#2401).** The rule runs in both directions, and the `Unit/` side needs it too: four files there carried `uses(TestCase::class)` against the Layout table's contract, so the directory was not framework-free as documented. Each was qualified the same empirical way — drop the mixin, run it. One qualified and stayed, its mixin removed: `Support/Forms/ChoiceSubmissionLimitsTest.php`, 24 tests in 0.06 s. Three threw `A facade root has not been set.` and moved to their mirror paths under `tests/Feature/` keeping the mixin — `Support/Http/OutboundUrlGuardTest.php` (69 tests), `Support/Forms/FormRestrictionsTest.php` (12), `Listeners/HashVisibilityPasswordTest.php` (10). No assertion changed in any of the four, and the same 115 tests pass in their new homes. Those three are already empirically qualified as needing the container, so they are **not** candidates for the UAMS-Web/uams-statamic-archive#1317 long-tail audit — re-running it on them would repeat a decided question. To check the contract still holds, `grep -rl 'Tests\\TestCase' tests/Unit --include='*.php'` must return nothing, and the same grep over `tests/Feature` must still return files — otherwise an empty result is only evidence the grep is blind.

## Rendering a template in a test — pass `trusted: true`

`Statamic\Facades\Antlers::parse()` takes a third parameter that decides which of **two different
rendering regimes** you get, and the unsafe call looks identical to the safe one:

```php
// vendor/statamic/cms/src/View/Antlers/Antlers.php:30-34
public function parse($str, $variables = [], $trusted = false)
{
    $parser = $this->parser();
    $previousState = GlobalRuntimeState::$isEvaluatingUserData;
    GlobalRuntimeState::$isEvaluatingUserData = ! $trusted;
```

Defaulting `$trusted` to `false` renders inside Antlers' **user-content sandbox**. Production never
does: `Engine::get()` routes every view through `RuntimeParser::parseView()`, which forces that flag
**off**.

The two regimes do not merely differ in strictness — **they render differently.** In the sandbox an
augmented `entries` relation reaching a `{{ pair }}` is silently reduced, so an empty-relation
fall-through *cannot occur*. A test asserting that markup is absent therefore passes no matter what
the template says: a green that survives deleting the code under test, which neither `--mutate` nor
a code review reliably catches, because the test is genuinely green and the mutation genuinely makes
no difference **in that regime**.

That is not hypothetical. UAMS-Web/uams-statamic-archive#2026 fixed exactly this fall-through on the shared post card. UAMS-Web/uams-statamic-archive#2031 then
concluded the News block was exempt — and was wrong; the block carried the same defect, and the
only reason its harness could not see it was that it parsed the partial's source as a string while
the post card's harness rendered `{{ partial:posts/card }}`. Results were compared across two
harnesses that differed in the one dimension that mattered.

**So, when a test renders a template:**

- Prefer `Antlers::parse('{{ partial:some/partial }}', $data)` — a literal partial tag puts the
  partial body on the trusted path automatically, which is what production does.
- If you must render a source string (`file_get_contents` of a partial, or an extracted slice),
  pass `trusted: true` explicitly.
- An **inline snippet** is *not* automatically safe. `$isEvaluatingUserData` gates several
  behaviors, and every one of them degrades **silently** — `errorOnAccessViolation` is unset, so
  each logs a warning and carries on:
  - a deferred `Value` (a relation, a query builder) reaching a `{{ pair }}` is **reduced**;
  - `ModifierManager::guardRuntimeModifier()` consults an **allow-list** and, on a miss, silently
    `continue`s past the modifier instead of loading it — so an unregistered modifier never reaches
    `Loader::load()` and never throws;
  - the equivalent allow-list applies to **tags**;
  - a **method invocation** (`{{ obj.method() }}`) is popped and replaced with `null`
    (`Sandbox/Environment.php`);
  - a **PHP node** (`{{? … ?}}`, `{{$ … $}}`) is sanitized rather than executed
    (`NodeProcessor.php`).

  Do not treat that list as exhaustive — an earlier version of this section said "three things" and
  was wrong, which is why the rule below is phrased as a default rather than a checklist.

  The second one is not theoretical. `NewsBlockTest`'s UAMS-Web/uams-statamic-archive#76 regression guard exists to fail if an
  invalid modifier is reintroduced into the News block partial, and it was structurally incapable of
  doing so: untrusted, `| int` was skipped in silence and the test stayed green. Under `trusted: true`
  it throws `ModifierNotFoundException` as intended. `SeoMetaPartialTest` had the same shape — the
  sandbox blocked `{{ glide }}`, so two image tests were asserting on template literals outside the
  tag rather than on any output.

  **So default to `trusted: true` whenever a render does anything beyond reading scalars and
  printing them.** The flag costs nothing and is never wrong for a harness, because production is
  always trusted; enumerating what is safe to leave untrusted has been got wrong repeatedly.

**Prove the test can fail.** An assertion that markup is *absent* passes when the render fails, when
the branch is not taken, or when the fixture is malformed. Delete the markup from the template and
watch the test go red before trusting it — and mutate to something that does not *contain* the
asserted substring (`<section` → `<div`, not `<sectionXX`, which still contains `<section`).

UAMS-Web/uams-statamic-archive#2040 audited the suite for this. Every `Antlers::parse()` call under `tests/` was classified with
PHP's own tokenizer — comments dropped, first argument bucketed by what it *is* rather than by a
sigil — because four successive grep heuristics produced four wrong answers before that.
Every site that rendered a real template file untrusted was converted — eleven here, plus the SEO
head partial's own in UAMS-Web/uams-statamic-archive#2050. Afterwards, of **451 calls: 317 take a literal first argument, 102 a
non-literal trusted one, and 32 a non-literal untrusted one** — and none of those 32 reads a
template file; every one is an inline snippet or a `{{ partial: }}` literal built by concatenation.
The bullet above is how to judge whether yours is one.

Re-derive the figures with `token_get_all()`, not a grep. Four successive grep heuristics gave four
wrong answers here: an end-of-line anchor that counted multi-line calls, a same-line `trusted: true`
regex that misread them, a match inside a comment, and bucketing on a `$` sigil — which missed every
site whose first argument is a helper call or a `file_get_contents(...)` expression, including the
one on the News block partial this audit was named for.

## Test helper classes — one PSR-4 file each, never inline

A named helper **class** a test needs (a stub, a fake tag/fieldtype, a fixture builder) goes in **its own file** whose name matches the class and whose namespace matches its directory under the `Tests\ => ./tests` PSR-4 rule — e.g. `Tests\Feature\Views\StubUamsNewsTag` in [`Feature/Views/StubUamsNewsTag.php`](Feature/Views/StubUamsNewsTag.php), `use`-imported by the test. **Do not** declare a named `class` inline inside a Pest test file: Pest files carry no namespace, so an inline class lands in the global namespace and Composer skips it with a `does not comply with psr-4 autoloading standard` warning on every `composer dump-autoload` (issue UAMS-Web/uams-statamic-archive#1026).

Global *function* helpers (the Pest idiom) are fine inline, or shared via a required file like [`Support/CpSmoke.php`](Support/CpSmoke.php); reusable *traits* mixed into test cases live in [`Concerns/`](Concerns/README.md). This rule is only about named **classes**.

## Never `use`-import a global class in a Pest file

The same "Pest files carry no namespace" fact has a second, louder consequence. A **non-compound** import in a test file — `use ReflectionProperty;`, `use Throwable;`, `use ArrayObject;` — raises PHP's `The use statement with non-compound name 'X' has no effect`. Laravel's `Illuminate\Foundation\Bootstrap\HandleExceptions` promotes that warning to an `ErrorException`, and Pest's `TestSuiteLoader` trips it while scanning **every** test file. So one such import anywhere kills the entire `pest --parallel` band at load: roughly 17s, no `Tests:` line, no failing test named — just an `ErrorException` and the file that carries it.

Write the bare name instead. In the global namespace `new ReflectionProperty(...)` already resolves to the global class, and a leading-backslash `\ReflectionProperty` is equivalent — Pint's `fully_qualified_strict_types` normalizes the second form to the first, which is fine either way. Only the `use` line is the problem.

**Assume nothing else will catch it.** It does not reproduce on `pest <file>`, on an explicit multi-file list, or on `--group=serial` when the offending file is not in that group — all of those skip the whole-suite scan. Pint and Larastan both pass on the file. It shipped past five green checks here before a full band caught it, which is the same "full suite only" shape as two same-named top-level helper functions colliding. The isolation guard below now reports both shapes before the band runs.

## CI

The PHPUnit job in `.github/workflows/ci.yml` runs the suite **in parallel** (`pest --parallel`, paratest). The Statamic stache is warmed once per PHP process by the test bootstrap (`Tests\CreatesApplication`), so each parallel worker warms its own isolated per-`TEST_TOKEN` file cache (`config/cache.php`) — there is no longer a separate `statamic:stache:warm` CI step. Feature tests that resolve real taxonomy terms, asset containers, or entries from `content/` rely on this; unit tests should not.

Tests that depend on the `content/` submodule should mix in [`Concerns/RequiresContentSubmodule`](Concerns/README.md) so they **skip gracefully** when it is absent (a bare worktree, or `local-ci --skip-submodule`) rather than failing. CI and `local-ci.mjs` initialize `content/`, so they run there as normal — and there a lookup that resolves nothing **fails** instead of skipping, since with the submodule present a `null` is a defect rather than an absent submodule (UAMS-Web/uams-statamic-archive#1738). Pick the guard that matches what you are asserting: `requireContentEntry()` / `requireContentCollection()` for a lookup that must resolve, `skipWithoutQualifyingContentEntry()` for an editorial precondition the content set is free not to satisfy. [`Concerns/README.md`](Concerns/README.md) has the full contract.

### Mutation testing — author-side by design, with a tooling smoke on the gate

Real mutation runs are **deliberately outside the gate.** The [`adversarial-review`](../.claude/rules/adversarial-review.md) rule scopes them per-change and author-side: after fixing a real bug, run `composer mutate -- --class="App\<Class>"` over the changed surface and close every surviving mutant (a survivor is a false-green test, or dead code to delete). A diff-scoped mutation *job* is the theoretically right answer and stays unbuilt — it needs a reliable changed-file-to-class mapping and costs minutes rather than seconds (UAMS-Web/uams-statamic-archive#1731).

What **is** gated is the **tooling**, via the `mutate` job in [`ci.yml`](../.github/workflows/ci.yml) and [`scripts/local-ci.mjs`](../scripts/local-ci.mjs): one narrowly-scoped run over `App\Support\UamsAlert\AlertSiteKeyResolver`, asserting a non-zero mutation count and a 100% score.

That distinction is the whole point. **UAMS-Web/uams-statamic-archive#1728 was not a mutant escaping a weak test** — it was `pest-plugin-mutate` silently reporting `0 Mutations for 0 Files created` after a `php-code-coverage` bump. Pest exits `0` on that, so nothing anywhere went red, and the tool the review rule leans on was quietly dead for as long as nobody ran it by hand. Hence the job asserts the **count and the score**, not the exit code, and there is no "skip when no coverage driver" fallback — a skip would be a false green about false greens. The job therefore makes a coverage driver (PCOV or Xdebug) a machine-level requirement; see the [`pcov-setup`](../.claude/skills/pcov-setup/SKILL.md) skill.

`0 Mutations for 0 Files created` **always means the run found nothing to mutate — a setup failure, never a pass.**

### Parallel-fragile tests (the `serial` group)

A set of tests (77 files after the 2026-09-16 audit below, 73 once UAMS-Web/uams-statamic-archive#2503 returned four more, 37 once UAMS-Web/uams-statamic-archive#2501 returned 36, and 40 once UAMS-Web/uams-statamic-archive#3205 returned three of the gates added since, not a handful; 39 by `pest --group=serial --list-tests` at `3ac22cfa4`, each with a row below; `ParallelSafeTestsGuardTest` had a row until UAMS-Web/uams-statamic-archive#3210, though it names `serial` only inside fixture strings and was never in the group) is not run concurrently: e.g. a test that hardcodes a shared file path, races on a Windows file lock inside the per-worker cache, or writes to a `Storage::persistentFake` disk, whose root carries no worker token, so every worker shares it. The CI job runs the suite in two steps: `pest --parallel --exclude-group=serial` for the bulk, then a single-process `pest --group=serial` tail for these.

When a test proves parallel-fragile, **prefer a real fix over the serial group where the cause is known and the fix is clean** — most often the cause is a hardcoded shared path, which should be made per-run by appending `Tests\Support\ThrowawayRoot::segment()` **inside** the `storage_path()` call. Fall back to the `serial` group only for fragility that is unpinnable or genuinely unfixable in parallel:

> **Use the helper, not a bare `env('TEST_TOKEN')`.** That expression was the convention until UAMS-Web/uams-statamic-archive#1957, and it was half a fix twice over. `TEST_TOKEN` is set solely by paratest, so every *serial* run fell through to one shared segment and two of them wiped each other's fixtures (UAMS-Web/uams-statamic-archive#1957); and it is the worker **index**, 1..N, which repeats across runs, so two concurrent *bands* put worker 3 of each on one path for the same reason (UAMS-Web/uams-statamic-archive#1960). `ThrowawayRoot` now ends every segment in the process id — `<worker index>-<pid>` under paratest, `seq-<pid>` serially — because no two processes alive at once can share a pid, while the index alone guarantees nothing across runs. A config path read in **production** follows the same rule inside its `TEST_TOKEN` conditional, so production and serial runs keep the shared default: `config/cache.php` and `config/tables.php` append `<token>-<pid>` since UAMS-Web/uams-statamic-archive#1985, which measured the collision on Windows (nine of ten concurrent bands failing, none after). `SeedTestStache` still clears the shared `data/` parent, and each worker deletes its own `<token>-<pid>` directories when it exits.

- **Pest tests:** chain `->group('serial')` on the `it(...)`/`test(...)` call, or on `uses(...)` to cover a whole file.
- **PHPUnit class tests:** add a `#[Group('serial')]` attribute (or `@group serial` docblock) to the method or class.

Keep the group small and **name each member** (with the reason) so the exclusion stays honest and reviewable. The list below is the UAMS-Web/uams-statamic-archive#2291 audit of every member, and it is the record a new gate joins: add the row when you add the gate, with the mechanism and the pull request.

#### What the tail costs, and where (UAMS-Web/uams-statamic-archive#2291)

The group was 83 files when audited on 2026-09-16, and for 41 of them no reason was recorded in the file or in the pull request that added the gate -- most were gated at authoring time during the July 2026 render-flake wave (UAMS-Web/uams-statamic-archive#1300 / UAMS-Web/uams-statamic-archive#1310 / UAMS-Web/uams-statamic-archive#1447 / UAMS-Web/uams-statamic-archive#1452) by convention rather than on an observed failure. The audit therefore records a **mechanism** per file (what the gate is protecting against) and a **verdict**, and reads runs only as refutation, per the constraint the ticket's first pass established: a `--parallel` run whose failure set changed between two runs (4 to 7 distinct files, five of seven appearing in exactly one) can falsify "safe to move" and can never establish it.

**The cost is concentrated, not spread.** Measured from the gate's own `junit-serial.xml` on macOS, 2026-09-16, parity with the `phpunit` job (route cache on, seeded, the job's flags): the tail's 502 tests sum to **386.4s** of test time against a ~508s wall (the rest is per-test boot in one process). Three files were 54% of it -- `SitemapTaxonomyTermsTest` **122.2s** in one test, `AssetsMinimumDimensionsEnforcementTest` 53.0s, `AssetsByFileTypeScopeTest` 31.6s -- and the 40-odd render and scope files everyone assumed were the tail sum to a couple of minutes. The 122s was not the gate: `Term::save()` and `Term::delete()` with events dispatch `Statamic\Search\UpdateItemIndexes`, a `ShouldQueue` listener that runs inline under the suite's sync queue across every local search index — 3.78s on the save and 116.85s in the teardown that queried and deleted (instrumented), the mechanism `TaxonomyTermArchiveTest` already records for the same term (UAMS-Web/uams-statamic-archive#1634). With `saveQuietly()` and `deleteQuietly()` the same test, same sweep, runs in 0.92s and the file in 2.27s. The two asset files' ~8s a test was mostly Statamic's asset reference sweep on each `afterEach` delete, not their `Stache::clear()` (UAMS-Web/uams-statamic-archive#2504). UAMS-Web/uams-statamic-archive#2500 switches the sweep off around those deletes in all four asset files that pay it, and narrows the clear; the per-test figures after it await a measurement on a quiet machine.

**So the single-process constraint is inherent for the files that record a reason, and irrelevant to most of the cost.** Two mechanisms are closed on both platforms: the compiled-view cache is per worker under Laravel's `TestViews` (`storage/framework/views/test_<token>`, the directory UAMS-Web/uams-statamic-archive#2442 patched for concurrent bands), and every worker has warmed its own cache from one snapshot since UAMS-Web/uams-statamic-archive#1590. ### Enforcing it — the isolation guard

The convention above is enforced, not just documented. [`scripts/check-parallel-safe-tests.php`](../scripts/check-parallel-safe-tests.php) (issue UAMS-Web/uams-statamic-archive#1149) statically scans `tests/` (over PHP tokens, so matches inside comments and string literals are ignored) and fails the build when a test uses a parallel-unsafe, shared-state pattern **without** quarantining it:

- **Rule A**: `Storage::persistentFake(` (roots the disk at `storage/framework/testing/disks/<name>` with no worker token, so every worker shares it). A plain `Storage::fake(` is not flagged: under `--parallel` it appends `_test_{TEST_TOKEN}` to the root, so each worker fakes its own (UAMS-Web/uams-statamic-archive#3111, measured against `laravel/framework` v13.37.0; the script header has the citation).
- **Rule B**: `storage_path('…framework/testing…')` with no per-run uniqueness token (`ThrowawayRoot`, `uniqid`, `TEST_TOKEN`, `random_bytes`, `Str::random`, `bin2hex`) anywhere in the call. The token must sit **inside** the call: Rule B reads the call's own tokens, so hoisting it to a local first hides it and reds the job.

A file is exempt when it is quarantined **whole-file** into the `serial` group (a Pest `uses(...)->group('serial')` chain, or a class-level PHPUnit `#[Group('serial')]` / `@group serial`) and, independently, exempt from the rules a row in the script's `ALLOWLIST` names for it, with a reason. A row suppresses only the rules it lists (`['rules' => ['B'], 'reason' => '…']`), so the file is still checked for the others (UAMS-Web/uams-statamic-archive#2939). A per-`it()` / per-method `serial` marker quarantines only that test, so it does **not** exempt the file (a sibling `Storage::persistentFake` in a parallel test is still flagged). It runs as the dedicated `test-isolation-guard` CI job (mirrored by `--jobs isolation` in `scripts/local-ci.mjs`) and is dependency-free: run it locally with `php scripts/check-parallel-safe-tests.php`. It catches the disk/path leak classes above; it does **not** catch shared *tool-cache* races (e.g. a test shelling out to Pint/Rector), which still need per-run cache isolation or the `serial` group.

The same job then runs the shared [`check-global-test-symbols.php`](../.claude/skills/pest-testing/scripts/check-global-test-symbols.php) over `tests/` (UAMS-Web/uams-statamic-archive#3112). It reports the two global-scope defects above, which the private script used to carry as Rules C and D:

- **Rule C**: a global `const` or `function` declared in more than one namespace-less file. Function names compare case-insensitively, as PHP does.
- **Rule D**: a single-segment `use X;` in a file with no named namespace.

Neither the `serial` group nor the `ALLOWLIST` exempts a file from these two. The serial tail runs every quarantined file in one process, so two serial files declaring the same helper collide there too, and a no-op import is dead code wherever it runs. Run it locally with `php .claude/skills/pest-testing/scripts/check-global-test-symbols.php tests`.
