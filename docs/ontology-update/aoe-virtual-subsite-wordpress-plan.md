# UAMS Find-a-Doc Ontology Overhaul — WordPress Plan as Designed & Partially Built (Epic FD20-2671)

This document is the canonical record of the WordPress-side plan for **FD20-2671 "Changes to Ontology Items to Expand Medical Services Web Content"** — the overhaul that demotes Conditions & Treatments from full pages to plain search keywords and retools every Area of Expertise (AoE, CPT handle `expertise`) so it presents like its own *virtual subsite*: its own site header, primary navigation, breadcrumbs, permalink space, and programmatically-generated "fake subpages" (Providers, Locations, Specialties/child AoEs, Related AoEs, Clinical Resources), capped by a Make-an-Appointment CTA bar. It is the input to a later conversation about porting this to Statamic; per item it flags *likely-to-port* vs *likely-moot*, with the schema.org/JSON-LD strand called out as probably-not-porting. The crucial framing fact: **almost none of this shipped** — only the data-model carve-out (FD20-3862/FD20-3873) reached production; the entire subsite experience lives, unmerged and stale, on a single integration branch.

**Sources.** This synthesis draws on three primary sources: the 38 FD20 Jira tickets, each cited by its key (the raw exports are not kept in this repository), read-only git archaeology of the `UAMSWP-Find-a-Doc` repo, and the project's working document — *"UAMS Health Find-a-Doc Area of Expertise Update / Schema To Do List"* (`docs/ontology-update/google-doc-aoe-schema-todo.md`), the companion that tracked the schema.org strand and its supporting data-model design as the tickets were worked. Where the three disagree, code reality wins and the gap is called out.

## The vision & the ontology model

The conceptual spine is the **"ontology item vs. simple content" discriminator** from **FD20-3256**. Every `expertise` post carries one ACF `true_false` field, `expertise_type` ("What Type of Content Is This Page?", `ui_on="Expertise"`, `ui_off="Content"`, default `1`). Non-zero (or unset) = an **AoE Ontology Item** — the subsite root; `0` = an **AoE Content Item** — a simple content page nested under one. This is the load-bearing concept for the rebuild: a *single collection* whose entries are either a full subsite or simple content gated by one flag. The glossary FD20-3256 pins (AoE Ontology Item, AoE Content Item, AoE Overview Page, Fake Subpages, ancestor/descendant relative to the current item) is the vocabulary the rest of the epic uses.

**Reality check on FD20-3256:** the discriminator exists **only for `expertise`** — there is no `condition_type`/`treatment_type` equivalent; conditions and treatments are demoted wholesale, so "simple content" is an `expertise`-only concept in code, not a generic ontology-CPT idea. The field's *consumers* were built on the FD20-3311 branch: ancestor-walking that keeps only ontology-type ancestors for breadcrumbs/top-level resolution (`class.fad-functions.php` ~2014); a two-bucket child query splitting `expertise_type != 0` (descendant AoEs) from `= 0` (a separate "content" nav section, ~2961/3012); a relationship-field filter (`uamswp_fad_relationship_ontology_type`, `class.fad-acf-functions.php` ~2197/2201) that excludes simple-content pages from being "associated" as ontology relations (explicit comment: "0 means Simple Content Item"); and `expertise_save_post_before` (~483) which forces the landing-page header style for ontology items. **Two FD20-3256 acceptance criteria were never finished** — the *conditional display/disable* of the Content Type input (top-level must be Ontology, descendant-of-Content must be Content) and the *conditionally-required-and-filtered parent input* that sets the WP post parent; a comment on the ticket (2023-06-26) records work stalling on exactly these plus deep-descendant exclusion in the Associated AoEs field. A port must replicate the **"unset means Ontology Item"** default, or every legacy AoE page would silently flip to simple content.

**What actually shipped (FD20-3862 + FD20-3873).** This was the deliberately-scoped releasable-in-advance subset, forked clean from master so content entry could begin early. It did three big things, all additive and on production today:

- **Taxonomy layer** — renamed many taxonomies (Medical Departments → Clinical Departments, Clinical Titles → Clinical Specializations, Boards & Certifications → Specialty and Subspecialty Certificates, etc.); added four net-new taxonomies (`brand_organization`, `brand_organization_uams`, `certifying_body`, `parking`); deactivated `department` (commented, not deleted — term data may persist); collapsed board-certification flat fields into a single taxonomy reference field; made the degree taxonomy non-hierarchical.
- **Term-level ACF (the structural insight that should inform the rebuild)** — structured reference data moved *onto terms, not posts*. The centerpiece `group_uamswp_clinical_specialization.json` attaches to the **existing `clinical_title` taxonomy** (note: `clinical_specialization` is **not** a taxonomy — it is merely the field-handle prefix on `clinical_title` terms) and carries NUCC code, patient-friendly occupation title, CMS Specialty Code, Schema.org MedicalSpecialty member, O*Net-SOC, ISCO-08 (radio), and UAMS-extension qualifications. Other term groups give `brand_organization` a full Schema.org Organization shape, `parking` a ParkingFacility shape, `language` Romanized native name (endonym) + BCP47, etc. A hierarchical *inherit-from-parent* save hook lets a child `clinical_title` term inherit code-set values via `*_inherit_query` toggles (`class.fad-acf-functions.php` ~821).
- **Occupational-title derivation (FD20-3873)** — provider `physician_title` is an ACF taxonomy field bound to `clinical_title`; the rendered title now derives from the term's `clinical_specialization_title`, with a hardcoded **"Resident Physician"** special case that, when `physician_resident` is set, short-circuits the term-derived title and emits the literal string `"Resident Physician"` (bypassing the `clinical_title` term lookup entirely), applied consistently across provider card, loop card, recognition shortcode, REST API, and AJAX filters. FD20-3873 also opportunistically fixed a *pre-existing* resident-default-selection bug unrelated to FD20-3862.
- **Facility/parking model + structured provider-name components (the schema working doc's design that actually shipped).** FD20-3862 also landed a `building` taxonomy whose *Facility Item Configuration* term group (`group_uamswp_building.json`) realizes the working doc's complex→building facility hierarchy — place-subtype radios for building vs complex, full address/region/GPS, a `facility_parking` reference into the new `parking` taxonomy, GLN, and brand-org — plus the working doc's **structured provider-name** components on `group_uamswp_physicians.json` (`physician_first_name`/`_middle_name`/`_last_name`, `physician_pedigree` generational suffix, `physician_full_name`/`_medium_name`, and the `physician_alternatename` clone). These are the *blueprint-relevant* parts of the schema working doc that reached production; the parts that did **not** are catalogued in the next subsection.

Critically, FD20-3862 also staged the **AoE fake-subpage override fields** (`expertise_{providers,locations,descendant,associated}_fpage_{intro,short_desc,featured_image,...}` plus `expertise_region`) and the per-section label option pages — **data only**. Verified absent on master: any `add_rewrite_rule` / `template_redirect` / fpage routing or template. The virtual-subsite *substrate* is in production; the *behavior* is not.

### Companion data model from the schema working doc (blueprint-relevant, partly unbuilt)

The *Schema To Do List* is ~90% schema.org property emission (catalogued under *Schema.org structured data* below, and likely moot), but it also specifies real **data-model / blueprint** design that outlives JSON-LD. Build status here is verified against the field groups, not assumed from the doc:

- **Structured provider name — partly shipped.** The name *components* landed in FD20-3862 (first/middle/last, generational suffix, full/medium name, alternate-name repeater). **Not built:** the *name-display-format selector* (per-part include toggles so editors mirror the external name defined in Epic), an explicit *nickname* field with presence/absence button groups, and the *hidden search-only concatenation* field meant to feed provider search + site search across every name variant. Design intent only.
- **Facility / Building / Parking taxonomy — largely shipped.** The `building` taxonomy + *Facility Item Configuration* group and the separate `parking` taxonomy are in production (FD20-3862). The working doc's *consuming behavior* is the unbuilt remainder: a Location **inheriting** address/GPS/parking from its Facility term (hiding the Location's own building fields when a Facility term is set, with per-field override toggles), two-level-hierarchy enforcement (buildings only under complexes), and `containedInPlace` parent display.
- **Education & Training + credentials — design intent.** An *Education and Training Organization* taxonomy and an *ACGME-accredited specialty/subspecialty programs* taxonomy (to drive `hasCredential`/`EducationalOccupationalCredential`, distinguishing degree vs residency/fellowship, sponsoring org vs clinical site, ACGME-accredited or not) are specified but are **not** present as field groups — master ships `degree`, `certificate`, `certifying_body`, and `language` instead. De-duplicating the education/training list against the Clinical Degrees & Credentials list is an open task.
- **Recognition List taxonomy — design intent.** A taxonomy + field group to construct provider/location *award* text (list name, publishing organization, year) and surface it in an awards section. A `templates/blocks/recognitions.php` exists, but the structured taxonomy/field-group is working-doc intent.
- **Known bugs recorded in the working doc** (candidate rebuild test-cases, or discard as WP-only): the descendant-locations section renders but shows **no cards** (`$location_count` forced to 0 in `templates/parts/vars/page/queries/location.php`); the provider **breadcrumb shows the post title** instead of the formatted name; schema `image`/`mainEntity` arrays **double-count** (items plus node references to those same items); and the **Clinical Resource schema function is disabled** in `includes/find-a-doc.php` pending work.

For the Statamic conversation, the shipped pieces (name components, facility/parking taxonomies) are blueprint *facts*; the unbuilt pieces are open design the rebuild can adopt, simplify, or drop.

## The subsite experience (chrome)

This is the "make each AoE look and navigate like its own microsite within `/expertise/`" presentation layer — seven FD20-2671 child stories (FD20-3257/3258/3259/3260/3262/3266/3317). All of it is unmerged on the FD20-3311 branch, and "subsite identity" everywhere resolves to a computed `$site_nav_id`: an ontology-type AoE is its own subsite; a content-type AoE inherits the chrome of its **nearest ontology-type ancestor**. The chrome is delivered entirely through **Genesis theme hooks** — `construct-body.php` does `remove_action` on the host UAMS-2020 theme's site image, primary nav, and entry header, then `add_action`s AoE-specific replacements onto `genesis_header` / `genesis_after_header` / `genesis_before_content`. None of that hook plumbing survives a Statamic rebuild; the requirements do.

- **Site header (FD20-3257)** — `site-header/single-expertise.php` replicates the UAMS-2020 header but swaps the `navbar-subbrand` for the AoE title (closest-ancestor logic) plus a parent link to the *farthest* ontology ancestor (with an equality check suppressing the parent slot when closest == farthest). Per-item glyphs show Providers/Locations/Clinical-Resources/Related-AoE propagation reached "DONE on the epic branch," but the main-page, Specialties, descendant-content, and most subbrand logic only reached a developer's fork. The ticket is **Blocked on FD20-3261** (header suppression on the fake subpages of *deeper* descendant ontology items can't be verified until multi-level fake-subpage URLs work).
- **Primary nav (FD20-3258)** — `site-nav/single-expertise.php` is a hand-built Bootstrap nav: "Overview" + one conditional link per populated section (Providers/Locations/Specialties/Related/Resources), each pointing at `get_permalink($site_nav_id) . '<sub>/'` and gated by a `$<type>_section_show` flag, each marked up as a `SiteNavigationElement`. **Confusing dead code:** it calls `wp_nav_menu(['menu'=>'expertise-navigation'])` into `$nav` but **discards the result** — the `expertise-navigation` menu is never registered anywhere — and a `WP_Bootstrap_Pagewalker` for descendant AoEs is assembled but its output isn't clearly emitted. Treat the nav as the fixed-link list. FD20-3258 is **Blocked on the walker-menu requirement** (mirroring the full descendant content-item hierarchy) — the same multi-level recursion problem that blocks 3257/3260.
- **Breadcrumbs (FD20-3259) — NOT BUILT.** This is the clearest "ticket implied but not built" gap. The AoE breadcrumb function `uamswp_cpt_breadcrumb()` and its `genesis_cpt_crumb` filter in `class.fad-helper-functions.php` are **fully written then entirely commented out and never registered** (helper-functions.php:523/577); a repo-wide grep for any uncommented breadcrumb `add_filter` returns nothing. Genesis breadcrumb customization was abandoned in favor of **SEOPress filters** — the fake-subpage breadcrumb crumb is appended via `seopress_pro_breadcrumbs_crumbs` in `fpage/construct-body.php`, and canonical via `seopress_titles_canonical`. So only the *fake-subpage crumb* exists; per-AoE breadcrumb trails and the FD20-3259 acceptance criteria (fake subpage in crumbs only when active; archive label from the Find-a-Doc Settings plural form — the item recorded as unresolved) are **intent only.**
- **Permalink structure (FD20-3260) — the root blocker.** Fake-subpage URLs at Level 1 (`/expertise/foo/providers/`) work; **Level 2 and Level 3** (arbitrary intermediate AoE subdirectories) do not. Work stalled on adjusting `add_rewrite_rule()` for "infinite subdirectories," and this single WordPress-rewrite-API limitation **cascades** into FD20-3257 (header suppression/verification) and the broader chrome. The child-AoE rewrite (`expertise/(.+?)(?:/([0-9]+))?/<slug>/?$`) was the attempt; the deep-nesting cases remained the blocked items.
- **Page headers (FD20-3262)** — status QA, on a developer's fork only. Removes the "None" header style on AoE pages; **forces** "Marketing Landing Page" on ontology pages (parent AoE omitted there since it's already in the site header); uses "Graphic" on fake subpages; offers Graphic (default)/Marketing Landing/Hero on content pages with the selector **restricted to admins**. Implemented via swappable `entry-title/{normal,graphic,landingpage}.php` parts keyed off `$entry_header_style` (forced to `graphic` for fpages).
- **Guard rails (FD20-3266)** — status QA, a developer's fork only: required featured image constrained to ~16:9, required excerpt capped at 160 chars. The override-field plumbing exists on master (FD20-3862), but the *required + aspect-ratio + char-limit enforcement* is unmerged. Note FD20-3310 later proposed *removing* the featured-image requirement (rewriting it as an optional override of settings-level default images) — an internal tension to reconcile.
- **Normal-header consideration (FD20-3317)** — a "[Consider]" follow-up to FD20-3262: allow the "Normal" style on content pages one level removed from their ontology ancestor. Explicitly deferred, To Do; enabling it forces expanding the block whitelist beyond UAMS blocks.

## Fake subpages — the central mechanism

This is the heart of the vision (**FD20-3261**), and it is genuinely built (minus deep nesting). "Fake subpages" are virtual URLs `expertise/<aoe-slug>/<fpage>/` where `<fpage>` is one of exactly five fixed slugs — `providers`, `locations`, `specialties`, `resources`, `related` — that resolve to the *real AoE post* plus a custom `fpage` query var. They are not real WP posts; it's the classic WP "fake pages" pattern (the file header credits ~2012 betterwp.net / placementedge.com posts).

**How it works in code:** `includes/class.fad-expertise-rework.php` (new on the branch, `include_once`d from `find-a-doc.php`) runs `fsp_insertrules()` on `init`, looping a hardcoded five-slug map and registering two top-priority rewrite rules per slug (top-level + child-AoE forms), all rewriting to `index.php?expertise=$1&fpage=<slug>`; `fsp_insertqv()` whitelists `fpage`. `class.fad-templates.php`'s `uamswp_force_template()` (on `template_include`) dispatches empty-`fpage` → `single-expertise.php` and each slug → `single-expertise-<slug>.php`. Each thin entry template includes shared `common/` + `fpage/` construction parts; `fpage/vars.php` is the dispatch core — it maps the slug to a variable-name prefix held in `$fpage_var_name` (`providers→provider`, `specialties→expertise_descendant`, `related→expertise`, etc.) and derives title/intro/short-desc/featured-image from per-fpage ACF fields via PHP **variable-variables** (`${ $fpage_var_name . '_fpage_title_expertise' }`, vars.php:37), then forces `entry_header_style='graphic'` and sets the canonical to `$fpage_url`. **Operational footgun:** no `flush_rewrite_rules()` / activation hook — the file comment tells the admin to visit Settings → Permalinks and Save. **Known smell:** `ontology-subsection.php` injects ~17 variables into template scope via `${$key}=$value`, leaking extras (`$conditions_cpt`) that several `schema_*.php` files have explicit "Band-aid" `unset()`s for.

The **list data** comes from `uamswp_fad_ontology_site_values()` (`class.fad-functions.php` ~1972), transient-cached per page: providers from the `physician_expertise` relationship, locations from `location_expertise`, related AoEs from `expertise_associated`, clinical resources from `expertise_clinical_resources` — but **child AoEs ("specialties") uniquely come from the WP page hierarchy** (`get_pages(child_of=$site_nav_id, post_type='expertise')`), excluding descendant simple-content items. So AoE parent/child is modeled as WP `post_parent` nesting; a port must decide whether AoE hierarchy is a Statamic structure/nav tree or an entries relationship.

**FD20-3261's blocker** is the same Level-2/Level-3 URL problem as FD20-3260 (functional URLs for fake subpages under non-top-level ontology items). **Decided & dropped:** the per-page *title* override was struck out across all subpage types; only the lead-paragraph override survives.

The surrounding fake-subpage tickets are mostly **deferred or design questions**, and several were never built:

- **References to other item lists (FD20-3310)** — To Do, real work on the rolling branch (placeholder branch = `df7c957a`). A large Find-a-Doc Settings inventory: per-archive/subpage *default images* (sized for the Text & Image Overlay block) and per-reference Title/Body/Link text for many combinations, plus the rule that each subpage references its main archive and (when not top-level) its top-level-AoE counterpart, rendered as a CTA bar (one reference) or text-and-image overlay (two). This also *removes* the featured-image requirement from FD20-3266 (see tension above). Largely a settings-inventory task.
- **Multi-level aggregation (FD20-3309)** — a pure, unresolved **design fork** (no code): does each subpage list items for *this* ontology item only, or aggregate across *all descendant* ontology items? It enumerates the same choice for provider/location/related/clinical-resource subpages, and asks whether the Specialties subpage shows all descendants or only immediate. This drives query scope across the whole system and is **undecided**.
- **Related-vs-descendant merge (FD20-3312)** — a single-question "Consider": merge the descendant-AoE listing into the related-AoE subpage? **Undecided**, and it *gates* FD20-3273.
- **Fake descendant AoEs (FD20-3273)** — Phase 2: a new relationship for cross-hierarchy plan-of-care links (e.g. physical therapy ↔ orthopaedics), shown in descendant lists but visually distinct. **Conditionally moot** — self-disregards if FD20-3312 merges related and descendant into one section.
- **Simple-content menu placeholders (FD20-3265)** — Consider/Phase 2: nav items linking *outside* the AoE hierarchy. Geonetric audit feedback favors the opposite — keep site-specific nav and force a context page before linking away. **Undecided.**
- **Appointments & Referrals subpage (FD20-3272)** — Phase 2: a sixth fake-subpage type with separate patient/physician guidance, new Find-a-Doc Settings field groups, and references to the top-level and main appointment pages. **Not built** (no sixth slug exists; the five are hardcoded).

## Blocks & content-composition rules

The headline here — the **allowed-blocks whitelist (FD20-3263)** — is genuinely built, small, and clean; but **four of the five "new block" tickets were never built as blocks at all.** FD20-3263 is one `allowed_block_types_all` filter (`class.fad-functions.php` ~11252) that, *for the `expertise` post type only*, replaces the full palette with a curated 15-slug "marketing/landing-page" list (`acf/action-bar`, `acf/call-out`, `acf/counter-list`, `acf/cta`, `acf/fad-locations`, `acf/fad-providers`, `acf/image-side`, `acf/link-list`, `acf/livewhale-calendar`, `acf/logo-list`, `acf/text-overlay`, `acf/text-stacked`, `acf/uams-gallery`, `acf/uams-section`, `acf/uams-news`; `acf/hero` and `acf/uams-content` deliberately commented out). 13 of the 15 are **theme-owned** (uams-2020), not plugin blocks. The aspirational settings-driven toggle UI for maintaining the whitelist was *not* built; FD20-3263's ticket is **Blocked on FD20-2914**.

- **FaD locations/providers blocks (FD20-3314)** — effectively a no-op decision ticket on this branch: `acf/fad-locations` and `acf/fad-providers` (real ACF blocks registered via `acf_register_block_type`, **not** `block.json`) and their `filter_aoe` Area-of-Expertise filter field **already existed on master**; the branch only refactors them. So AoE-filtering capability predates the integration branch.
- **Appointment CTA Bar block (FD20-3264) — NOT a block.** No commit, registration, render callback, or template matches FD20-3264. The whitelisted `acf/cta` is a *theme* block, and the appointment bar is rendered in templates as a CSS `cta-bar` module (`templates/parts/html/section/appointment.php`), not a purpose-built block. The ticket's rich spec (three phone inputs, referral toggle, settings → nearest-ontology-ancestor → per-page inheritance, locked-vs-auto-append fork) is **intent only.**
- **AoE-reference / fake-page-linking block (FD20-3315) — NOT a block.** The "links to each fake subpage" capability is satisfied by the routing/template system (rewrite rules + `single-expertise-*` templates), not a Gutenberg linking block. The composite-vs-individual layout fork is undecided. Spec only.
- **Conditions/treatments listing block (FD20-3316) — NOT a block.** No matching registration/template. Note its role *shifts* anyway since C&T are demoted to simple text.
- **Min/forced blocks (FD20-3313) — NOT built.** It depends conceptually on 3315/3316 (which don't exist) and is **Blocked** on the unsolved problem of applying *locked blocks conditionally by post meta* (force on ontology items, never on content items) — the ticket records doubt that it is possible at all.
- **Fly Image Resizer dimensions (FD20-3281)** — a small supporting task to make the resizer optionally return `{url, width, height}` for `og:image:width/height`. To Do, unmerged, and **likely obsolete in Statamic** (Glide handles resizing and dimensions).

For a port, the *whitelist intent* maps to Bard/Replicator set restrictions and the inheritance hierarchy to computed properties — but **the four unbuilt block tickets carry no code; they must be designed fresh if still wanted.**

## Conditions & Treatments demotion

The second half of the epic — strip Conditions & Treatments of their own web presence and reduce them to keywords/text. Built on the FD20-3311 branch, **not on master** (on master the C&T templates are still force-loaded and there is no C&T redirect).

- **Disable singles/archives + redirect (FD20-3267)** — Blocked. The build **comments out** (does not delete) the six condition/treatment branches in `uamswp_force_template()` (single/archive/taxonomy for both CPTs), so the templates still exist but are unreachable; and adds a `template_redirect` 301-redirecting every condition/treatment single *or* archive to the home URL with UTM tracking (`utm_medium='redirects'`, `utm_campaign='redirects_404'`, `utm_content='single-…'/'archive-…'`, `utm_source` = stripped permalink). **Verified bug:** the `is_single()` branch writes the slug to an undefined `utm_specs` key (with `.=` rather than assigning to `utm_content`) at `class.fad-templates.php:205` instead of `utm_content` (PHP notice; cosmetic UTM defect — the redirect still works). The ticket is **Blocked** on the *WordPress-admin-chrome* suppression items recorded as unresolved — hiding the Gutenberg editor for a post type, hiding third-party plugin panels (SEOPress) per post type, and hiding the Permalink/Template rail panels. The redirect/UTM, hide-fields, featured-image hiding, and the two **"Searchable" toggles** (`condition_searchable` / `treatment_procedure_searchable`) reached a developer's fork. The admin-chrome suppression is the most WP-specific and **likely-moot** piece.
- **Convert to simple text (FD20-3269)** — QA, furthest along (AoE variants merged to the epic branch; provider/location/clinical-resource variants + the "exclude from Remove Medical Ontology Options" cleanup + new bullet/column styling on a developer's fork). Wherever conditions/treatments are listed on provider/location/AoE/clinical-resource singles, a shared part (`templates/parts/html/section/list/condition-treatment.php` after the FD20-3261 refactor) renders each title; the `$condition_treatment_section_link_item` flag **defaults to false and is never set true by any caller**, so items always emit as plain `<span class="item">Title</span>` — the "link items" path is effectively dead code. An open **"Consider"** remains: whether to merge the Conditions and Treatments lists into one on FaD pages.
- **Related clinical research (FD20-3477)** — Never started (To Do, "Relates to" the epic, not a child). Additive, not demotive: structure and display clinical-research articles on AoE/Location subsections, modeled on the Proton Center page. Heavily schema.org-framed (MedicalScholarlyArticle / MedicalStudy / `subjectOf` / `about`), making it the **likeliest of the three to be moot** for the rebuild.

## Schema.org structured data — likely moot for Statamic

**Flag this entire strand as probably-not-porting.** FD20-3311 ("Ensure proper schema data on AoE page and fake subpages," In Progress, ~5 weeks logged) is the namesake of the canonical integration branch, but it is a large, **still-WIP** JSON-LD engine, and structured data is typically re-solved at the Statamic/SEO-addon layer rather than ported function-for-function. Catalog, do not invest.

What it built: per-CPT `@graph` builders (`class.fad-schema-array-{provider,location,expertise,condition,treatment,clinical-resource}.php`; the provider builder is ~9,966 lines, the AoE one ~3,840, condition ~1,517, treatment ~1,865) emitting `MedicalWebPage` + per-type entities (provider → MedicalBusiness + Person; location → LocalBusiness; expertise → MedicalEntity; clinical-resource → CreativeWork; condition → MedicalCondition with `signOrSymptom`/`identifyingTest`/`identifyingExam`; treatment → MedicalProcedure/MedicalTest/Service with `signDetected`/`medicineSystem`/`code`). A generic resolver (`includes/schema/schema-org.php`) drives construction from a types/properties map, and `uamswp_fad_schema_construct()` prints the `<script type="application/ld+json">`. **Evidence it's unfinished:** `schema_treatment.php` is a 34-occurrence all-`'foo'`/`'bar'` placeholder stub, the emitter still echoes a `<pre><code>` debug dump marked `// test` (schema-utility.php:804), and `_old`/`_wip` variants litter the directory. Condition/treatment schema functions are **nested-only** (never emitted standalone), consistent with those pages being redirected away.

The schema work has tendrils into the *shipped* FD20-3862 data model too: the `group_uamswp_schema.json` clone library (`schema_medicalspecialty_single`/`_multiple`) cloned into CPT "Schema Data" tabs, and the full Schema.org Organization shape on `brand_organization`. **The supporting research task FD20-3482** (To Do, action-flavor `hitl`, assigned to a team member) is a long stakeholder questionnaire (service-area definitions, currencies/payment methods, diversity/ethics statements, org identifiers — DUNS/ISIC/GLN/LEI/NAICS/VAT, capacity/employee counts, ratings/review aspects) that feeds exactly this strand — also **probably-not-porting**.

**What the working doc catalogs (by entity), for completeness.** The *Schema To Do List* is the authoritative inventory of this strand and is worth keeping as a checklist even if the engine is discarded. Per-entity property backlogs: **Provider** (aggregateRating, alternateName/legalName derived from the new name inputs, alumniOf, areaServed, award from Recognition Lists, hasCredential as EducationalOccupationalCredential, a long identifier set — DUNS/GLN/ISIC/ISO6523/LEI/NAICS/taxID/usNPI/vatID, keywords from location attributes, makesOffer, potentialAction, review); **Location** (acceptedPaymentMethod, award via a location-side Recognition taxonomy, contactPoint email/hours, ContactPointOption + a Language clone field beside every phone number, `department` for telemedicine hours, diversity/ethics policies, foundingDate, hasCertification vs hasCredential overlap, the same identifier set); **Area of Expertise** (code/identifier URL construction from a coding-system pattern, hasPart for MedicalWebPage, primaryImageOfPage from the landing-page header image, `speakable` via cssSelector on ≤550-char heading+paragraph blocks, study/citation, text/timeRequired derived from Gutenberg content, video); **Clinical Resource** (per-asset CreativeWork items — a large self-described WIP — with bitrate/duration/headline/inLanguage/isBasedOn/uploadDate, and VideoObject pulled from the YouTube-Lyte/Vimeo APIs); and **Condition/Treatment** (relationship-field schema subtypes — signOrSymptom/identifyingTest/identifyingExam/possibleTreatment/duplicateTherapy/signDetected — which *are* built on the field groups). Cross-cutting engine to-dos the doc opens with: a `which-schema-items-to-generate` argument, node-identifier de-duplication in `uamswp_fad_schema_add_to_item_values`, and transients for code-set/specialization lookups. The overwhelming majority of the per-property items are gated on **FD20-3482** stakeholder answers and were never emitted. **None of this is a port target** — Statamic structured-data is re-solved at the SEO-addon/template layer — but the *inventory of which properties UAMS cared about* is a useful starting checklist if structured data is rebuilt.

## Dependency & sequencing notes

The build had one **root blocker that cascaded**: **FD20-3260 (multi-level permalink/rewrite for fake subpages)**. Because deep-nested fake-subpage URLs never worked, FD20-3261 stayed Blocked, which in turn gated FD20-3257 (header suppression/verification on deeper descendants). The same multi-level-recursion shape independently blocked FD20-3258 (the walker menu) and the deep-descendant-exclusion item of FD20-3256. In short, **arbitrary tree depth was the unsolved engineering problem of the entire chrome layer.**

Beyond that:

- **FD20-3256** (ontology vs. content discriminator) is foundational — FD20-3257/3258 and the relationship-field filtering read `expertise_type`.
- **FD20-3261** (fake-subpage mechanism) is the parent of FD20-3310/3272/3273/3309/3312/3307/3308 — all of them assume fake subpages exist.
- **FD20-3255** (Find-a-Doc Settings) is the central dependency the templates *and* search (FD20-3254/3307) read labels/intros from.
- **FD20-3263** (block whitelist) is Blocked by **FD20-2914** and feeds FD20-3314/3315; **FD20-3313** (min/forced blocks) depends on FD20-3315 + FD20-3316 (both unbuilt) and on the unsolved conditional-locked-blocks-by-meta problem.
- **FD20-3279** (batch conversion) is Blocked by **FD20-2914** (the Gutenberg-block-move step).
- **FD20-3862 → FD20-3873** is the only fully-resolved, shipped chain.

Most of these relationships are *inferred* from the ticket text and code (the blocked-on notes in the tickets, the parent/child epic structure, and what each piece reads from another); only **FD20-3263→FD20-2914** and **FD20-3279→FD20-2914** are formal `blocked_by` edges on the tickets (per FD20-3263/3279). Treat the rest as analysis, not declared dependency links.

A Statamic rebuild can sequence very differently because the WP root blocker (the `add_rewrite_rule` recursion limit) **does not exist** — arbitrary-depth nesting is native to a Statamic structure/route layer — so the dependency graph collapses considerably once the data model (FD20-3256) and settings (FD20-3255) are expressed as blueprints/globals/computed fields.
